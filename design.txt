1. Executive Summary
The Tactive assessment is a one-week build-it-yourself engineering exercise. The candidate must create a working web application, use AI to generate and execute automated tests, deliberately demonstrate that tests detect a broken application, use an AI-driven change loop to implement a new feature and recover from regressions, and produce professional documentation, presentation material and a five-minute demo.
This documentation proposes a Turf Slot Booking System using React + Vite, a Go backend, and PostgreSQL. Authenticated users can view turf slots and reserve an available slot while the backend prevents conflicting active bookings. The scenario provides business rules, validation, authorization, state transitions, concurrency concerns and useful negative tests.
The central engineering story is the build → test → break → detect → fix → retest loop. AI is an assistant, not the verification mechanism.

3. Problem Statement
A turf-booking system must ensure that a user receives a confirmed reservation only when the selected slot is available. Frontend availability is not sufficient because multiple requests can arrive close together. The Go backend and database must be authoritative.
Core problem
Build a small web application where an authenticated user selects a turf, date and time slot and creates a booking. The system must prevent more than one active confirmed booking for the same slot.
Why this scenario works
Real business workflow rather than generic CRUD.
Clear rules become automated tests.
Normal, edge and invalid-input cases are meaningful.
Authentication and ownership create security cases.
Cancellation creates a state transition and regression opportunity.
Go demonstrates explicit handlers, services, database access and concurrency-aware backend design.
Scope is small enough for one week.

9.5 Database-level protection
Do not rely only on SELECT-then-INSERT. A PostgreSQL partial unique index can enforce the core invariant:
CREATE UNIQUE INDEX unique_active_booking_per_slotON bookings(slot_id)WHERE status = 'CONFIRMED';
The exact SQL must match the final schema. The Go repository/service should translate a uniqueness violation into a controlled 409 Conflict response.

11. Core Application Flows
11.1 Login
Login -> POST /auth/login       -> invalid: 401       -> valid: token/session -> Booking UI
11.2 Booking
Select turf/date      -> GET /slots      -> choose available slot      -> POST /bookings      -> Go handler      -> booking service      -> PostgreSQL constraint/transaction         -> conflict: 409         -> success: 201
11.3 Cancellation
Own confirmed booking -> POST /bookings/{id}/cancel -> ownership check -> deadline check -> status CANCELLED -> slot bookable again -> 200 OK
11.4 Concurrent booking
Request A ----                > PostgreSQL invariant -> exactly one active bookingRequest B ----/                         -> loser gets 409
This is important: UI checks cannot guarantee correctness under concurrency. The database must enforce the invariant.
12. Validation, Error Handling and Security
12.1 Validation
Reject missing fields.
Reject malformed JSON and UUIDs.
Controlled 404 for unknown resources.
Reject past dates where required.
Verify slot context.
Never trust browser-supplied user_id for ownership.
Use sensible request/body limits.
12.2 Authentication/authorization
Booking creation requires authentication.
Booking history is scoped to current user.
Modification checks ownership.
Do not expose another user's booking data.
Authentication middleware places verified identity in request context.
12.3 Go server concerns
Use request context for cancellation and DB calls.
Configure HTTP read/write/idle timeouts.
Never return stack traces/raw SQL errors.
Use structured logs without secrets.
Manage DB pool lifecycle.
Handle graceful shutdown.
12.4 Secrets
Environment variables for DB URL/JWT secret.
Commit only .env.example.
Add .env to .gitignore.
Never show credentials in evidence.
